# 不同分辨率编码时间分析报告

## 📋 执行摘要

本报告分析了 WebRTC 发送端在不同视频分辨率下的编码性能。数据来源于 `sender_local.log`。

## 🔍 关键发现

### 1. 分辨率变化过程

日志显示了以下分辨率变化序列：

```
1920x1080 (行213)
    ↓ [快速降级]
1280x720  (行235)
    ↓ [快速降级]
960x540   (行262)
    ↓ [快速降级]
640x360   (行275) ← 第一个实际编码的分辨率
    ↓ [运行一段时间后]
480x270   (行5989) ← 进一步降级
```

**重要观察**：
- 分辨率从 1920x1080 快速降级到 640x360，在**任何帧被编码之前**就完成了
- 第一个编码完成事件出现在行410，此时已经是 640x360
- 这是 WebRTC **Quality Scaler（质量缩放器）**的自适应行为

### 2. 为什么没有高分辨率的编码数据？

**原因分析**：

1. **软件编码性能限制**
   - 使用 OpenH264 2.6 软件编码器
   - 1920x1080 @ 30 FPS 对软件编码器来说计算量太大
   - CPU 无法在 33.33ms (30 FPS的帧间隔) 内完成编码

2. **Quality Scaler 机制**
   - WebRTC 检测到编码器负载过高
   - **预防性地**降低分辨率，避免积压和延迟
   - 在第一帧编码完成前就完成了降级
   - 目标：维持目标帧率 (30 FPS)

3. **降级速度**
   - 从 1920x1080 到 640x360 的所有降级发生在 **62 行日志内**
   - 表明系统检测到编码器无法处理高分辨率后立即响应

## 🔬 深度对比分析

### 分辨率与编码时间的关系

| 指标 | 640×360 | 480×270 | 差异 |
|------|---------|---------|------|
| 像素总数 | 230,400 | 129,600 (56.2%) | -43.8% |
| 平均编码时间 | 3.74 ms | 1.80 ms (48.1%) | **-51.9%** |
| 每百万像素编码时间 | 16.23 ms | 13.87 ms | -14.5% |
| 编码效率比 | 1.00x | 0.85x | +17.6% 效率提升 |

### 关键洞察

1. **编码时间降低幅度 > 像素降低幅度**
   - 像素减少 43.8%
   - 编码时间减少 51.9%
   - **说明**: 较低分辨率的编码效率更高（可能得益于缓存命中率、内存访问模式等）

2. **每百万像素编码时间**
   - 640×360: 16.23 ms/百万像素
   - 480×270: 13.87 ms/百万像素
   - 480×270 的编码效率高 **17.6%**

3. **两种分辨率性能都非常充足**
   - 640×360: 编码时间仅占帧间隔 11.2%
   - 480×270: 编码时间仅占帧间隔 5.4%
   - 都有大量性能余量

## 💡 建议与优化方向

### 1. 为什么系统选择降低分辨率？

虽然 640×360 和 480×270 编码性能都很好，但系统仍然降级，可能原因：

1. **网络带宽限制**
   - 不是编码性能问题，而是网络带宽不足
   - Quality Scaler 也会根据网络拥塞情况降低分辨率

2. **接收端性能限制**
   - 接收端解码能力可能不足
   - 降低分辨率减少接收端负担

3. **带宽估计保守**
   - GCC (Google Congestion Control) 估计带宽较低
   - 主动降低分辨率以避免丢包

### 2. 如何获得更高分辨率？

#### 选项 A: 启用硬件编码
```cpp
// 优先级：硬件编码 > 软件编码
// 当前使用: OpenH264 (软件)
// 建议使用: Intel QSV, VAAPI, NVENC 等硬件编码
```

**预期效果**：
- 1920×1080 编码时间可能降至 **5-10 ms**
- 可稳定支持 1080p @ 30 FPS

#### 选项 B: 调整 Quality Scaler 参数
```cpp
// 提高降级阈值，允许更高的编码器使用率
// 降低上升阈值，更积极地提升分辨率
```

#### 选项 C: 增加网络带宽预算
```json
{
  "video_encoder": {
    "max_bitrate_bps": 5000000,  // 当前可能限制较低
    "start_bitrate_bps": 2000000
  }
}
```

### 3. 稳定性优化

**问题**: 两种分辨率的变异系数都在 44-45%，稳定性较差

**原因分析**:
- I帧 vs P帧编码时间差异大
- 帧内容复杂度变化
- 编码器内部决策波动

**优化建议**:
```cpp
// 1. 使用固定关键帧间隔
keyframe_interval = 60;  // 每2秒一个I帧

// 2. 启用 CBR 模式获得更稳定的码率
rate_control_mode = CBR;

// 3. 使用更快的编码预设
encoding_preset = "ultrafast";
```

## 📈 性能总结

### ✅ 优势

1. **编码速度快**: 即使在软件编码下，640×360 和 480×270 都有大量性能余量
2. **零超时**: 没有编码超时帧，不会因编码性能导致掉帧
3. **高吞吐量**: 理论上可支持远超 30 FPS 的帧率
4. **自适应降级**: Quality Scaler 有效防止了系统过载

### ⚠️ 挑战

1. **无法维持高分辨率**: 1920×1080 立即被降级，未进行实际编码
2. **软件编码限制**: OpenH264 性能不足以支持高分辨率实时编码
3. **稳定性波动**: 编码时间变异系数较高 (>40%)
4. **分辨率下降**: 最终稳定在 480×270，低于常见视频会议质量 (720p)

### 🎯 核心结论

当前系统配置下（OpenH264 软件编码）：
- ✅ **640×360 及以下分辨率**: 性能充足，可稳定运行
- ⚠️  **1280×720**: 需要硬件编码支持
- ❌ **1920×1080**: 软件编码无法支持，必须启用硬件加速

**推荐配置**:
- 短期：优化网络带宽估计，尝试稳定在 640×360
- 长期：集成硬件编码器（QSV/VAAPI），支持 1080p @ 30 FPS
