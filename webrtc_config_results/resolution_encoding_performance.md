## 🔍 深度对比分析

### 编码效率对比

**每百万像素编码时间**：
```
1920×1080:  8.11 ms/百万像素 (基准)
1280×720:  11.98 ms/百万像素 (效率降低 48%)
960×540:   17.00 ms/百万像素 (效率降低 110%)
640×360:   18.05 ms/百万像素 (效率降低 123%)
```

**观察**：
- ⚠️  **分辨率越低，每像素编码成本越高**
- 原因：OpenH264 对大块处理更高效，小分辨率相对开销（初始化、帧管理）占比更大
- 结论：从编码效率角度，**1080p 最划算**

---

### 像素减少 vs 时间减少对比

| 分辨率降低 | 像素减少 | 编码时间减少 | 效率提升 |
|-----------|---------|-------------|---------|
| 1080p → 720p | 55.6% | 34.4% | **不成比例** |
| 720p → 540p | 43.8% | 20.2% | **不成比例** |
| 540p → 360p | 55.6% | 52.8% | **接近线性** |

**结论**：
- 高分辨率降级的性能提升**不成比例**
- 低分辨率之间的性能提升接近线性
- **1080p → 720p** 像素减少 55.6%，但编码时间仅减少 34.4%

## 📉 稳定性分析

| 分辨率 | 标准差 | 变异系数 (CV) | 稳定性 |
|--------|--------|--------------|--------|
| 1920×1080 | 5.55 ms | 33.0% | ⚠️  中等 |
| 1280×720 | 3.17 ms | 28.7% | ⚠️  中等 |
| 960×540 | 3.34 ms | 37.9% | ⚠️  中等 |
| 640×360 | 2.69 ms | 64.8% | ❌ 较差 |

**观察**：
- 所有分辨率的变异系数都偏高 (> 20%)
- **640×360 稳定性最差** (CV = 64.8%)
- 原因：I帧 vs P帧编码时间差异大

**变异系数说明**：
- CV < 20%: 稳定性好
- 20% ≤ CV < 40%: 稳定性中等
- CV ≥ 40%: 稳定性差

## 💡 优化建议

### 针对 1920×1080

**问题**: 2.7% 超时率，稳定性中等

**建议**:
1. **启用硬件编码** (QSV/VAAPI)
   - 预期编码时间降至 5-8 ms
   - 超时率降至 0%

2. **优化编码参数**
   ```cpp
   // 降低复杂度
   complexity = LOW_COMPLEXITY;

   // 使用更快的运动搜索
   motion_search = FAST;

   // 减少 B 帧
   max_b_frames = 0;
   ```

3. **动态调整 GOP**
   - 当检测到编码过慢时，增加 keyframe_interval
   - 减少 I 帧频率

### 针对所有分辨率

**问题**: 稳定性普遍中等偏差 (CV > 30%)

**建议**:
1. **码率控制优化**
   ```cpp
   // 使用 VBR 替代 CBR
   rate_control_mode = RC_QUALITY_MODE;

   // 允许更大的码率波动
   max_bitrate = target_bitrate * 1.5;
   ```

2. **Scene Change Detection**
   ```cpp
   // 启用场景检测
   scene_change_detection = true;

   // 场景切换时强制 I 帧
   force_iframe_on_scene_change = true;
   ```

3. **固定 Slice 大小**
   ```cpp
   // 使用固定 slice 大小提高稳定性
   slice_mode = SM_FIXEDSLCNUM_SLICE;
   slice_num = 4;
   ```

## 🔬 技术总结

### 重要发现

1. ✅ **OpenH264 软件编码器可以实时编码 1080p @ 30 FPS**
   - 平均 16.82 ms，仅占帧间隔 50.5%

   - 720p: 67% 余量
   - 540p: 74% 余量
   - 360p: 88% 余量
